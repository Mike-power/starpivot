# 应急重规划场景设计（v0.4 计划）

> 起草于 2026.9.25。v0.1~v0.3 回答了「链路稀缺时静态调度怎么做」，
> v0.4 回答真实系统真正难的那个问题：**动态不确定下如何在线重规划**。

## 1. 动机与论文价值

现有实验全部是静态设定：任务集仿真前固定、窗口集合固定，调度器本质上是
离线排程。但真实星地系统的灵魂是动态：

- 仿真窗口丢一个、任务顺序就全变；
- 窗口可能临时取消（天气、地面站冲突、卫星机动）；
- 应急任务（突发观测请求、异常处置指令）中途插入，优先级最高。

**叙事价值**：论文 introduction 的弧线可以从「链路稀缺是默认状态」推进到
「稀缺之上还有不确定——静态最优调度在真实环境中必然失效，需要在线
重规划机制」。这直接支撑创新点①（通信窗口感知的星地分层推理调度方法）
的专利交底书：静态调度是权利要求的基础，应急重规划是方法的核心防御性
特征。

## 2. 场景定义：三类应急事件

| 事件 | 参数 | 物理含义 |
|---|---|---|
| **应急任务插入** | 插入率 r_task（0/5%/10%），应急任务 deadline 极紧（1800s） | 突发观测请求、异常处置 |
| **窗口丢失** | 丢失率 r_win（0/10%/20%） | 天气、地面站冲突、卫星机动 |
| **窗口抖动** | 偏移 Δ（±300s，低概率） | 轨道预报误差、站间协调偏差 |

应急任务的关键设计矛盾：**应急任务往往 complexity 高（需要地面大模型），
但 deadline 紧（等不起窗口）**——这正是「星上硬解 vs 地面精准」冲突的
最尖锐形态，也是星地分层调度价值的最好展示场景。

## 3. 模型扩展

- `Task` 增加 `priority: int = 0`（0=常规，1=应急），`Metrics` 增加
  应急任务成功数/常规任务成功数分列统计
- 新指标维度：
  - **应急成功率**（系统对最不能失败任务的保障能力，主指标）
  - **应急代价** = 常规任务成功率下降幅度（抢占公平性）
  - **重排次数**（重规划机制本身的开销代理）

## 4. 调度策略对比（消融设计）

| 策略 | 说明 | 检验的问题 |
|---|---|---|
| 静态 EDF | v0.3b 原样跑，遇到应急事件不重排 | 静态调度在动态环境下的退化幅度（基线） |
| 抢占式 EDF | 应急任务到达即抢占队列头部，常规任务顺延 | 抢占的收益与对常规任务的代价 |
| 抢占 + 可行性检查 | 抢占的同时对顺延任务做重检，必死者快速失败 | 发现 3 的机制在动态环境是否依然成立 |

## 5. 实现计划

1. `emergency.py`（新模块）：事件驱动在线调度循环——事件队列包含
   任务到达、窗口开始、窗口丢失/抖动；队列状态在每个事件点重排
2. `scenario.py`：扩展 `gen_tasks` 支持应急插入 + 事件序列生成（固定种子可复现）
3. `run_emergency.py`：r_task × r_win 双因素扫描 × 5 种子，
   结果落 `benchmark/results/emergency_v0.4.md`

实现要点：在线循环复用 v0.3 `_serve_pending` 的窗口内服务逻辑，
但把「一次性静态排序」改为「每个事件点重排候选队列」，
保证 v0.3 与 v0.4 在同一服务语义下可比。

## 6. 预期发现（可证伪的假设）

1. 应急率 5% 时，静态调度的应急成功率比抢占式低 15 点以上
   （假设：应急任务 deadline 紧，静态排队等不起）
2. 抢占的常规任务代价 < 10 点（假设：应急任务占比小，代价可控）
3. 窗口丢失率 20% 时，可行性检查的收益进一步放大
   （假设：发现 3 的 scarcity regime 机制在动态环境下增强）

## 7. 边界与不做的事

- 不做星上算力动态变化（轨道进出阳照区功率波动）——留作后续工作
- 不做多星协同（单星场景已足够支撑论文主结论）
- 应急事件参数先用合成分布，TLE 接入沿用现有 `timeline_tle.py` 复用
